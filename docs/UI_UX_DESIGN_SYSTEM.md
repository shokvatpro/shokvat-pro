# هيكل الواجهة ونظام التصميم — شوكفات برو
**UI_UX_DESIGN_SYSTEM.md** · الإصدار 0.1 (مسودة للاعتماد)

> التصور البصري المبدئي (الهوية + 5 شاشات) معروض على لوحة التصميم «شوكفات برو — تصور الهوية» للمراجعة. هذه الوثيقة توثّق القرارات المتخذة فيها وتكمل الهيكل.

---

## 1. مبادئ التجربة
1. **موظفة الاستقبال أولًا:** المهمة الأكثر تكرارًا (الرد + الحجز) ≤ 3 نقرات.
2. **العربية أولًا، الإنجليزية كاملة:** لا شاشة تُصمم بالإنجليزية ثم «تُقلب».
3. **ما يحتاج انتباهًا يظهر أولًا:** المتأخر عن SLA والمكالمات الفائتة في أعلى القوائم.
4. **الصدق في البيانات:** لا أرقام وهمية تبدو حقيقية؛ شارة «بيانات تجريبية» واضحة؛ الأرقام التقديرية موسومة.
5. **الخصوصية مرئية:** أقنعة للأرقام في القوائم، ولا محتوى رسائل في الإشعارات على الشاشة المقفلة.
6. **سرعة محسوسة:** هياكل تحميل (Skeletons)، تحديث فوري، اختصارات لوحة مفاتيح.

## 3. فصل هوية المنصة عن هوية المجمع

| | هوية المنصة (شوكفات برو) | هوية المجمع |
|---|---|---|
| يتحكم بها | مالك المنصة | مدير المجمع (صلاحية `branding.manage`) |
| تظهر في | الدخول العام، لوحة المنصة، التسعير، الفواتير، رسائل النظام | لوحة المجمع لموظفيه، النطاق الفرعي، اسم المرسل في البريد |
| القابل للتعديل | كل الرموز | **قائمة مسموحة فقط:** شعار فاتح/داكن، اسم العرض ar/en، لون التمييز، النطاق الفرعي، اسم المرسل |
| غير القابل للتعديل | — | ألوان الحالات، الخطوط، التخطيط، شارة «يعمل بواسطة شوكفات برو» |

**حماية لون المجمع:** عند الحفظ يُحسب التباين مقابل الأبيض والخلفية الداكنة؛ إن فشل (< 4.5:1) يُشتق تلقائيًا أقرب درجة ناجحة وتُعرض معاينة.

**تحميل الهوية:** من `tenant_branding` حسب المجمع النشط ← متغيرات CSS على عنصر الجذر (`--tenant-primary`…). لا تُخزَّن مؤقتًا بشكل مشترك بين المجمعات.

**رفع الشعار:** PNG/SVG حتى 1MB، تنقية SVG من السكربتات، توليد نسخ بأحجام متعددة.

## 4. معمارية الرموز (Design Tokens)

```
packages/design-tokens/
  tokens/
    platform.json        # الأساس (مقفل)
    themes/light.json    # ربط دلالي: bg, surface, text, primary …
    themes/dark.json
    tenant.schema.json   # المفاتيح المسموح للمجمع بتجاوزها فقط
  build/ → css variables · tailwind preset · TS types · (لاحقًا) React Native
```
- صيغة متوافقة مع **W3C Design Tokens (DTCG)**؛ البناء عبر Style Dictionary.
- Tailwind يقرأ المتغيرات الدلالية فقط (`bg-surface`, `text-muted`, `bg-primary`) — يُمنع استخدام قيم hex مباشرة في المكونات (قاعدة lint).
- الوضع الداكن: `class="dark"` + احترام إعداد النظام + اختيار المستخدم المحفوظ.
- تعديل الهوية مستقبلًا = تعديل ملف JSON وإعادة البناء، دون لمس المكونات.

## 5. مكتبة المكونات (packages/ui)
**الأساسية:** Button، IconButton، Input، Textarea، Select، Combobox، Checkbox، Radio، Switch، DatePicker (يدعم RTL)، TimePicker، PhoneInput (E.164)، Badge/StatusPill، Avatar، Tooltip، Dialog، Sheet/Drawer، DropdownMenu، Tabs، Toast، Skeleton، EmptyState، Pagination، DataTable (فرز، فلاتر، تمرير أفقي على الجوال).

## 9. الإتاحة
- WCAG 2.2 AA هدفًا؛ تباين 4.5:1 للنص.
- كل عنصر تفاعلي عنصر HTML حقيقي (button/a/input) مع تسمية.
- التنقل الكامل بلوحة المفاتيح؛ مؤشر تركيز واضح.
- لا يُعتمد على اللون وحده للحالات (نص + أيقونة).
- `prefers-reduced-motion` محترم.
- اختبار مع قارئ شاشة بالعربية (VoiceOver/NVDA) قبل الإطلاق.

## 10. نبرة النصوص
- عربية فصحى مبسطة، مباشرة، مخاطبة الموظف بلطف («لم تُرسل الرسالة لأن…» بدل «خطأ 470»).
- أفعال واضحة على الأزرار («إنشاء موعد» لا «موافق»).
- قاموس مصطلحات موحّد (محادثة، عميل، موعد، مجمع، فرع…) في `packages/i18n/glossary`.

## 11. المخرجات التالية في مرحلة التصميم
1. اعتماد الألوان والخطوط والشعار (هذه الوثيقة + لوحة التصميم).
2. تصميم الشاشات المتبقية (العملاء، المواعيد، الموظفين، التقارير، الفواتير، التكاملات، الإشعارات، الإعدادات، الدول، إدارة المجمعات).
3. حالات فارغة/خطأ/تحميل لكل شاشة.
4. اختبار قابلية الاستخدام مع 3–5 موظفات استقبال على نموذج تفاعلي.
5. تسليم الرموز في `packages/design-tokens` وبناء Storybook.
