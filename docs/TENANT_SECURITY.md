# أمن المستأجرين وحماية البيانات — شوكفات برو
**TENANT_SECURITY.md** · الإصدار 0.1 (مسودة للاعتماد)

> لا تدّعي هذه الوثيقة امتثالًا قانونيًا. الهدف ضوابط تقنية تجعل الامتثال ممكنًا بعد مراجعة قانونية مستقلة لكل دولة.

---

## 1. تصنيف البيانات

| الفئة | أمثلة | الحساسية | أين تُخزن |
|---|---|---|---|
| C4 — صحية محتملة | محتوى الرسائل، المرفقات، تسجيلات المكالمات، الملاحظات الداخلية | **عالية جدًا** | Data Plane فقط، مشفّرة |
| C3 — شخصية | اسم العميل، رقمه، معرفات القنوات، المواعيد | عالية | Data Plane فقط |
| C2 — تشغيلية للمجمع | الموظفون، الفروع، الإعدادات، رموز القنوات (سرية) | متوسطة/سرية | Data Plane (رموز مشفّرة) |
| C1 — اشتراك | اسم المجمع، الباقة، الفواتير، الاستخدام المجمع | متوسطة | Control Plane |
| C0 — عامة | صفحات التسويق، الأسعار المعلنة | منخفضة | أي مكان |

**قاعدة:** كل محادثة تُعامل كـ C4 افتراضيًا، حتى لو بدت عادية.

## 2. طبقات العزل بين المجمعات (Defense in Depth)

| الطبقة | الضابط |
|---|---|
| 1. الشبكة | لا وصول مباشر لقواعد البيانات من الإنترنت؛ شبكات خاصة لكل منطقة |
| 2. المنطقة | رمز الوصول يحمل `region`؛ `tenant-api` يرفض أي رمز لمنطقة أخرى |
| 3. التطبيق | `TenantContext` إلزامي في كل طلب (Guard في NestJS)؛ لا Repository يقبل استعلامًا دون سياق |
| 4. قاعدة البيانات | **RLS مع FORCE** + دور تطبيق بلا `BYPASSRLS` + Fail-closed |
| 5. التخزين | مسار الملفات `tenants/{tenant_id}/…` + روابط موقّعة قصيرة العمر (≤ 5 دقائق) تُصدر بعد فحص الصلاحية |
| 6. الوقت الفعلي | غرف WebSocket باسم `tenant:{id}:…`؛ الاشتراك يتحقق من العضوية في الخادم |
| 7. الطوابير | كل مهمة تحمل `tenant_id`؛ العامل يضبط RLS قبل أي استعلام؛ رفض المهام دون سياق |
| 8. الذاكرة المؤقتة | مفاتيح Redis مسبوقة بـ `t:{tenant_id}:` — لا ذاكرة مؤقتة مشتركة لبيانات المجمعات |
| 9. السجلات | تنقية المحتوى (no message bodies / phone numbers in logs) |
| 10. الاختبارات | اختبارات عزل آلية تمنع الدمج إن فشلت (§7) |

## 3. المصادقة

| البند | القرار |
|---|---|
| كلمات المرور | argon2id، حد أدنى 10 أحرف، فحص ضد قوائم كلمات مسرّبة (k-anonymity، دون إرسال كلمة المرور) |
| MFA | TOTP في MVP؛ **إلزامي** لإدارة المنصة ومديري المجمعات؛ اختياري قابل للفرض للموظفين؛ WebAuthn/Passkeys لاحقًا |
| الجلسات | Cookie httpOnly + Secure + SameSite=Lax، مدة نشاط 12 ساعة، «تذكّر الجهاز» 30 يومًا كحد أقصى، إلغاء من لوحة الإدارة |
| رموز الـ API | رمز وصول قصير (≤ 15 دقيقة) موقّع (EdDSA) + تجديد مقيّد بالجلسة |
| الحماية من التخمين | Rate limiting حسب IP والحساب، تأخير تصاعدي، قفل مؤقت، تنبيه |
| الاستعادة | رابط لمرة واحدة صالح 30 دقيقة؛ إلغاء كل الجلسات بعد تغيير كلمة المرور |
| SSO | OIDC/SAML لباقة المؤسسات (المرحلة 8+) |
| CSRF | رموز CSRF للطلبات المعدِّلة + فحص Origin |

## 4. الصلاحيات (RBAC)

### 4.1 أدوار المنصة (Control Plane)
| الدور | يستطيع | لا يستطيع |
|---|---|---|
| `platform_owner` | كل الإعدادات، الباقات، الدول، المجمعات، التحليلات المالية | قراءة محادثات/عملاء المجمعات |
| `platform_billing` | الفواتير، المدفوعات، الاشتراكات | تعديل الدول والمزايا |
| `platform_support` | التذاكر، طلب وصول مؤقت | أي وصول دون موافقة المجمع |
| `compliance_officer` | سجلات التدقيق، طلبات أصحاب البيانات، تقارير الوصول | التعديل التشغيلي |

### 4.2 أدوار المجمع (Data Plane) — افتراضية وقابلة للنسخ والتعديل

| الصلاحية | استقبال | خدمة عملاء | مشرف | تسويق | مدير فرع | مدير المجمع |
|---|---|---|---|---|---|---|
| `inbox.read.assigned` | ✓ | ✓ | ✓ | – | ✓ | ✓ |
| `inbox.read.all` (ضمن النطاق) | فرعه | – | ✓ | – | فرعه | ✓ |
| `inbox.reply` | ✓ | ✓ | ✓ | – | ✓ | ✓ |
| `inbox.assign` | – | – | ✓ | – | ✓ | ✓ |
| `contacts.read` | ✓ | ✓ | ✓ | – | ✓ | ✓ |
| `contacts.export` | – | – | – | – | – | ✓ (+ MFA حديث) |
| `contacts.merge` | – | – | ✓ | – | ✓ | ✓ |
| `appointments.manage` | ✓ | ✓ | ✓ | – | ✓ | ✓ |
| `reports.operational` | – | – | ✓ | – | فرعه | ✓ |
| `reports.marketing.aggregate` | – | – | – | ✓ | – | ✓ |
| `campaigns.manage` | – | – | – | ✓ | – | ✓ |
| `staff.manage` | – | – | – | – | فرعه | ✓ |
| `channels.manage` | – | – | – | – | – | ✓ |
| `settings.manage` / `branding.manage` | – | – | – | – | – | ✓ |
| `billing.view` | – | – | – | – | – | ✓ |
| `audit.view` | – | – | – | – | – | ✓ |

- **أخصائي التسويق لا يقرأ المحادثات** — يرى أرقامًا مجمّعة فقط.
- النطاق (Scope): `tenant` أو `branch`. الدور المقيّد بفرع لا يرى فروعًا أخرى (يُطبّق في الـ API وفي RLS عبر `app.branch_ids`).
- الإجراءات الحساسة (تصدير، حذف، تغيير صلاحيات، ربط قناة) تتطلب **إعادة تحقق MFA** خلال آخر 10 دقائق.
- مبدأ الأقل صلاحية: كل صلاحية جديدة غير ممنوحة افتراضيًا.

## 5. وصول دعم المنصة (Break-glass)
1. موظف دعم شوكفات يفتح طلب وصول مرتبطًا بتذكرة، مع سبب ونطاق (مثلًا: إعدادات القنوات فقط، أو محادثة محددة).
2. مدير المجمع يوافق أو يرفض من لوحته.
3. يُصدر رمز وصول خاص بدور `platform_support` مقيّد بالنطاق والمدة (افتراضي 60 دقيقة، حد أقصى 24 ساعة).
4. كل إجراء يُسجّل في `audit_log` للمجمع بنوع `platform_support` **ويراه المجمع**.
5. انتهاء تلقائي + إمكانية الإلغاء الفوري.
6. استثناء طارئ (حادث أمني) يتطلب موافقة `compliance_officer` + `platform_owner` ويُبلَّغ المجمع لاحقًا — **سياسة تحتاج اعتمادًا قانونيًا (Q-12)**.

## 6. التشفير وإدارة الأسرار
- **أثناء النقل:** TLS 1.2+ (يفضّل 1.3)، HSTS، لا HTTP.
- **أثناء التخزين:** تشفير الأقراص وقواعد البيانات والنسخ الاحتياطية بمفاتيح KMS **لكل منطقة**.
- **على مستوى الحقل:** رموز القنوات، أسرار MFA، الحقول الخام لنماذج العملاء المحتملين — Envelope encryption (مفتاح بيانات لكل مجمع مغلّف بمفتاح KMS للمنطقة) → يتيح «Crypto-shredding» عند حذف المجمع.
- **الأسرار:** في مدير أسرار سحابي؛ لا أسرار في المستودع أو متغيرات CI مكشوفة؛ فحص `gitleaks` في كل PR؛ تدوير دوري موثّق.

## 7. اختبارات العزل الآلية (إلزامية في CI)
لكل نقطة API ولكل جدول بيانات مجمع:
1. إنشاء مجمعين وهميين A و B.
2. مستخدم من A يحاول: قراءة/تعديل/حذف كائن من B عبر المعرّف المباشر ← **404** (لا 403، لعدم كشف الوجود).
3. البحث والفلاتر والتقارير والتصدير لا تُرجع بيانات B.
4. استعلام SQL مباشر بدور `app_user` دون ضبط `app.tenant_id` ← خطأ / صفر صفوف.
5. فحص آلي: كل جدول في `db-tenant` به `tenant_id` + RLS مفعّل + `FORCE` (اختبار يفشل إن أُضيف جدول دون سياسة).
6. WebSocket: مستخدم من A لا يستقبل أحداث B.
7. روابط الملفات الموقّعة لـ B ترفض جلسة A.
8. مهمة طابور بـ `tenant_id` مفقود تُرفض.
9. رمز وصول منطقة `sa-1` يُرفض في `eg-1`.

**بوابة الدمج:** أي فشل = منع الدمج إلى الفرع الرئيسي.

## 8. أمن التكاملات
- التحقق من توقيع كل webhook (HMAC-SHA256 لـ Meta، ومخطط كل مزود حسب توثيقه).
- رفض الأحداث القديمة (نافذة زمنية) + Idempotency عبر `provider_events`.
- الاستجابة السريعة (200) ثم المعالجة في الطابور؛ إعادة المحاولة بتراجع أُسّي؛ DLQ مع تنبيه.
- رموز OAuth للقنوات مشفّرة، مع تتبّع انتهاء الصلاحية وتنبيه قبل الانتهاء.
- قائمة سماح (Allow-list) لعناوين الاستدعاء الخارجي — لا SSRF.

## 9. أمن التطبيق
- التحقق من كل مدخل بـ Zod على الخادم.
- ترميز المخرجات؛ CSP صارم؛ منع تضمين الصفحات (frame-ancestors).
- فحص المرفقات: النوع الحقيقي (magic bytes)، الحجم، فحص فيروسات (ClamAV أو خدمة مُدارة) قبل إتاحة التنزيل.
- Rate limiting لكل مجمع ولكل مستخدم ولكل IP.
- ترويسات أمان قياسية؛ تحديث التبعيات آليًا (Renovate) مع مراجعة.
- مرجع التحقق: OWASP ASVS 4.0 المستوى 2 + OWASP API Top 10.

## 10. السجلات والتدقيق
- `audit_log` لكل: تسجيل دخول، فشل دخول، تغيير صلاحية، تصدير، دمج عملاء، ربط/فصل قناة، وصول دعم، تغيير إعدادات، حذف.
- لا يتضمن محتوى الرسائل.
- غير قابل للتعديل من التطبيق؛ يُحفظ وفق سياسة الدولة.
- لوحة لمدير المجمع لعرض سجل التدقيق وتصديره.

## 11. النسخ الاحتياطي والاستعادة والحوادث
- نسخ تلقائية + Point-in-time recovery داخل نفس المنطقة.
- **اختبار استعادة فعلي شهريًا** في staging وتوثيق النتيجة.
- خطة استجابة للحوادث: التصنيف، الاحتواء، التحقيق، الإبلاغ للمجمعات والجهات المختصة **وفق مهل كل دولة** (تُحدد قانونيًا)، المراجعة اللاحقة.
- Runbooks لكل سيناريو: تسرب رمز قناة، اختراق حساب مدير، فشل منطقة، حذف خاطئ.

## 12. الذكاء الاصطناعي وأدوات التطوير
- **لا تُرسل بيانات مرضى حقيقية إلى Claude Code أو أي مساعد برمجي**.
- أي ميزة ذكاء اصطناعي مستقبلية على محتوى المحادثات تتطلب: تقييم أثر (DPIA)، موافقة المجمع، مزود بشروط معالجة مناسبة، ومنطقة بيانات مقبولة.

## 13. ما يحتاج تحققًا مستقلًا
- اختبار اختراق خارجي قبل أي بيانات حقيقية.
- مراجعة قانونية لتصنيف المحادثات كبيانات صحية في كل دولة.
- مهل الإبلاغ عن الاختراق ومتطلبات مسؤول حماية البيانات لكل دولة.
