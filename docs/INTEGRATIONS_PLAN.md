# خطة التكاملات — شوكفات برو
**INTEGRATIONS_PLAN.md** · الإصدار 0.1 (مسودة للاعتماد)

> القاعدة: **تكاملات رسمية فقط**. لا scraping، لا أتمتة واتساب الشخصي أو واتساب ويب، لا تجاوز لقيود المنصات. نبني **محوّلات وهمية (Mock Adapters)** أولًا، ثم الحقيقية بعد تأكيد الإتاحة والصلاحيات وبيانات الاعتماد.
> تفاصيل واجهات المزودين (الصلاحيات، الأسعار، الإتاحة حسب الدولة) تتغير؛ يجب مراجعة التوثيق الرسمي لحظة التنفيذ.

| Facebook Messenger | مخطط | 5 | مراجعة تطبيق Meta للصلاحيات المطلوبة |

## 2. واجهات المحوّلات (Adapters)

```ts
interface MessagingAdapter {
  readonly provider: 'whatsapp' | 'messenger' | 'instagram' | 'tiktok_dm' | 'mock';
  verifyWebhook(req: RawRequest): VerifiedEvent[];          // يرمي خطأ إن فشل التوقيع
  normalize(event: VerifiedEvent): NormalizedInbound;        // رسالة/حالة/تفاعل
  send(msg: OutboundMessage, creds: ChannelCredentials): Promise<SendResult>;
  sendTemplate?(t: TemplateMessage, creds: ChannelCredentials): Promise<SendResult>;
  capabilities(): { templates: boolean; window24h: boolean; media: string[]; reactions: boolean };
}

interface LeadsAdapter { verifyWebhook(...); fetchLead(id, creds): Promise<NormalizedLead>; }
interface VoiceAdapter { verifyWebhook(...); normalizeCall(...): NormalizedCall; clickToCall?(...); }
interface PaymentAdapter {
  createCheckout(...); createSubscription?(...); refund(...);
  verifyWebhook(...); normalizeEvent(...): PaymentEvent;      // idempotent بالمعرف الخارجي
}
interface EmailAdapter { send(...) } ; interface SmsAdapter { send(...) }
interface SchedulingAdapter { listSlots(...); createBooking(...); syncStatus(...) }
```

كل محوّل له نسخة **Mock** تولّد أحداثًا واقعية (رسائل، حالات تسليم، مكالمات فائتة، نماذج عملاء) لتطوير الواجهات واختبار الأداء دون أي حساب حقيقي.

## 3. خط الاستقبال الموحّد (Ingress Pipeline)
1. نقطة webhook لكل مزود **في منطقة بيانات المجمع**.
2. التحقق من التوقيع (HMAC/مخطط المزود) + نافذة زمنية.
3. تحديد المجمع من معرف الحساب الخارجي (`channel_accounts.external_account_id`).
4. Idempotency: `provider_events (provider, external_event_id)` UNIQUE.
5. رد 200 سريعًا، ثم طابور `ingest.*`.
6. المعالجة: تطبيع ← جهة اتصال ← محادثة ← رسالة ← تعيين ← SLA ← إشعار ← حدث فوري.
7. الفشل: إعادة محاولة بتراجع أُسّي (حتى 8 محاولات) ← DLQ ← تنبيه + شاشة إعادة تشغيل للمشرف التقني.
8. **الترتيب:** حالات التسليم قد تصل قبل الرسالة؛ نحفظها مؤقتًا ونطبّقها عند وصول الرسالة.

## 4. واتساب — ملاحظات تنفيذية
- **Cloud API** من Meta (المستضاف لدى Meta) كخيار افتراضي؛ أو عبر BSP معتمد إن اختير — **(Q-03)**.
- **التسجيل المضمّن (Embedded Signup):** يتيح لكل مجمع ربط رقمه من داخل لوحتنا — يتطلب أن تكون شوكفات «شريك تقني/مزود حلول» وفق برنامج Meta. يحتاج تحققًا من الأهلية.
- **نافذة خدمة العملاء 24 ساعة:** خارجها لا يُرسل إلا قالب معتمد.
- **فئات القوالب:** خدمي (Utility) / تسويقي (Marketing) / مصادقة — لها تسعير مختلف حسب الدولة؛ النظام يحسب التكلفة ويعرضها.
- **الرقم:** رقم المجمع الحالي إن كان مستخدمًا في تطبيق واتساب العادي يحتاج ترحيلًا — يجب توعية العميل قبل الربط.
- **الموافقة:** الرسائل التسويقية فقط لمن لديه موافقة مسجلة في `consents`.

## 5. Messenger و Instagram
- تطبيق Meta واحد للمنصة مع صلاحيات الرسائل والصفحات؛ يتطلب **App Review** ووصف استخدام.
- نافذة الرد ووسوم الرسائل حسب سياسات Meta الحالية.
- بعض أنواع الرسائل والقصص والإشارات محدودة الدعم — توثق في `capabilities()`.

## 6. نماذج العملاء المحتملين (Meta / TikTok)
- اشتراك webhook لكل صفحة/معلن ← جلب تفاصيل النموذج ← إنشاء جهة اتصال + مهمة اتصال فورية + بدء SLA.
- حفظ `campaign_id` و `ad_id` و `form_id` لإسناد الحجز.
- الحقول الخام تُشفّر؛ لا نطلب في النماذج أسئلة صحية حساسة — **توصية للمجمعات**.

## 7. TikTok Business Messaging
- إتاحته محدودة حسب المنطقة والأهلية. يُبنى المحوّل الوهمي وواجهة القناة، وتبقى الميزة `blocked` حتى تأكيد رسمي مكتوب.

## 8. الاتصالات
- **المطلوب من المزود:** أرقام محلية، webhooks للمكالمات (رنين/رد/فائتة/انتهاء)، Click-to-call من المتصفح (WebRTC) أو تحويل لهاتف الموظف، سجلات المكالمات، تسجيل اختياري.
- **MVP:** تتبع المكالمات الفائتة + مهمة معاودة اتصال + سجل. التسجيل **معطّل افتراضيًا**.
- المرشحون: مزودون دوليون (Twilio/Vonage وأمثالهم) **لا يغطون بالضرورة كل الدول بأرقام محلية وبشروط ترخيص محلية** — مقارنة بمزودين محليين/إقليميين في كل دولة مطلوبة **(Q-04)**.

## 9. بوابات الدفع (اشتراكات شوكفات برو)
- المرشحون للتحقق: **PayTabs** (يذكر توثيقه دعم السعودية ومصر والإمارات وعُمان والكويت)، **Tap** (الخليج؛ يذكر توثيقه عدم قبول تجار مصر الجدد حاليًا)، **Moyasar** و **HyperPay** (السعودية)، **Paymob** (مصر)، **Stripe** (الإمارات — تحقق من دعم الكيان والدولة).
- الاختيار يعتمد على **مكان تأسيس كيان شوكفات** والتعاقد — **(Q-02)**.
- دعم: مدى/فيزا/ماستركارد، Apple Pay، المحافظ المحلية حسب الدولة.
- الاشتراكات المتكررة: باستخدام توكن البطاقة مع منطق التجديد لدينا (لا نعتمد على ميزة اشتراكات كل بوابة لتوحيد السلوك).
- Webhooks idempotent، مطابقة يومية (Reconciliation)، معالجة فشل الدفع: إعادة محاولة يوم 1/3/7، إشعارات، ثم `past_due` ← تعليق القراءة فقط بعد مهلة.
- **لا نخزن بيانات البطاقات** (صفحات دفع مستضافة / حقول مشفرة من البوابة) لتقليل نطاق PCI DSS.

## 10. البريد والـ SMS
- بريد معاملات: دعوات الموظفين، استعادة كلمة المرور، الفواتير، التنبيهات. من نطاق المنصة مع SPF/DKIM/DMARC.
- SMS: OTP احتياطي وتذكيرات مواعيد في الدول التي يفضّل فيها SMS — مع تسجيل اسم المرسل حسب الدولة.

## 11. ترتيب التنفيذ المقترح
1. Mock لكل القنوات + واجهة صندوق وارد كاملة (المرحلة 4).
2. البريد (المرحلة 3).
3. WhatsApp Cloud API في sandbox برقم اختبار (المرحلة 5).
4. Meta Lead Ads ← TikTok Leads ← Messenger/Instagram (المرحلة 5).
5. الاتصالات: المكالمات الفائتة فقط (المرحلة 5–6).
6. الدفع في sandbox (المرحلة 8).
7. TikTok DM عند تأكيد الإتاحة.

## 12. معايير قبول أي تكامل حقيقي
- كل حدث يظهر **مرة واحدة** وفي **المجمع الصحيح**.
- رفض أي webhook بتوقيع خاطئ (اختبار آلي).
- انتهاء صلاحية الرمز يُكتشف وينبَّه مدير المجمع قبل 7 أيام.
- أخطاء المزود تُعرض للموظف بلغة مفهومة («لم تُرسل الرسالة: انتهت نافذة الـ 24 ساعة، استخدم قالبًا»).
- مراقبة: معدل الفشل، زمن المعالجة، حجم DLQ لكل مزود.
