## المرحلة 1 — تحليل المنتج والمعمارية ✅ (هذه الوثائق)
**المخرجات:** الوثائق العشر في `/docs` + تصور الهوية.
**معايير القبول:**
- [ ] اعتمادك للقرارات الحرجة (قائمة Q في الملخص).
- [ ] اعتماد نطاق MVP.
- [ ] اعتماد فصل حالات المحادثة عن مراحل المسار.

## المرحلة 2 — نظام التصميم وتجربة المستخدم
**المهام:**
- إنشاء المستودع الخاص + monorepo + CI أساسي (lint/typecheck).
- `packages/design-tokens` (فاتح/داكن/مجمع) + Tailwind preset.
- `packages/ui`: 25 مكونًا أساسيًا + Storybook + اختبار axe.
- `packages/i18n` (ar/en) + قاموس المصطلحات.
- تصميم الشاشات الـ 15 (بما فيها حالات فارغة/خطأ/تحميل).
- نموذج تفاعلي للوارد والحجز + اختبار مع 3 موظفات استقبال.
**المخرجات:** Storybook منشور داخليًا، تصميمات معتمدة، رموز في الكود.
**معايير القبول:**
- [ ] كل مكون يعمل RTL/LTR وفاتح/داكن دون أخطاء axe حرجة.
- [ ] تغيير لون أساسي في ملف الرموز ينعكس على كل المكونات دون تعديل كود.
- [ ] موظفة استقبال تُكمل «رد + إنشاء موعد» في النموذج دون مساعدة في < 60 ثانية.

## المرحلة 3 — البنية متعددة المستأجرين والمصادقة
**المهام:**
- `control-api` و `tenant-api` و `worker` بهيكل NestJS.
- Postgres (control + tenant) + Drizzle + migrations + **سياسات RLS**.
- المصادقة: تسجيل، دعوة موظف، دخول، MFA (TOTP)، الجلسات، الاستعادة، Rate limiting.
- RBAC + الأدوار الافتراضية + نطاق الفرع.
- إدارة المجمعات (المنصة) + إعدادات المجمع + الفروع + الأقسام + الموظفون.
- إدارة الدول (تكوين) + توجيه المنطقة.
- سجل التدقيق، معالجة الأخطاء المركزية، المراقبة، فحص الأسرار في CI.
- البريد (Mock + مزود حقيقي في staging).
- البيانات الوهمية (3 مجمعات).
- docker-compose للتشغيل المحلي بأمر واحد.
**معايير القبول:**
- [ ] **كل اختبارات العزل (TENANT_SECURITY §7) تنجح** وتعمل في CI كبوابة دمج.
- [ ] كل جدول في `db-tenant` عليه RLS + FORCE (اختبار آلي).
- [ ] MFA إلزامي لأدوار المنصة ومديري المجمعات.
- [ ] تعطيل موظف يُنهي جلساته خلال < 60 ثانية.
- [ ] `pnpm dev` يشغّل النظام محليًا من الصفر.

## المرحلة 4 — CRM وصندوق الوارد (وهمي)
**المهام:**
- العملاء، الهويات، كشف التكرار والدمج، الوسوم، المسار، المهام.
- المحادثات، الرسائل، المرفقات (مع الفحص)، الملاحظات الداخلية، الردود الجاهزة.
- التعيين (يدوي، Round-robin)، SLA، التنبيهات، الحالات، `awaiting_agent`.
- الوقت الفعلي عبر WebSocket.
- البحث العربي والفلاتر.
- محوّلات Mock لكل القنوات + مولد حركة.
- **المواعيد الأساسية** (إنشاء من المحادثة، حالات) — إن اعتُمد Q-08.
**معايير القبول:**
- [ ] رسالة وهمية واردة تظهر للموظف المعيّن خلال < 3 ثوانٍ.
- [ ] FRT يُحسب صحيحًا بساعات العمل (اختبارات وحدات بحالات حدّية).
- [ ] تجاوز SLA يرسل تنبيهًا للمشرف.
- [ ] البحث «احمد» يجد «أحمد».
- [ ] اختبار حمل: 50 موظفًا متزامنًا، 20 رسالة/ثانية لمجمع واحد دون تدهور ملحوظ.
- [ ] لا تسرب بين المجمعات (اختبارات العزل للوحدات الجديدة).

## المرحلة 5 — التكاملات الرسمية
**المتطلبات المسبقة (خارج البرمجة):** Meta Business موثّق، تطبيق Meta، رقم اختبار، تطبيق TikTok.
**المهام:** WhatsApp Cloud API (وارد/صادر/حالات/قوالب/نافذة 24 ساعة) ← Meta Lead Ads ← TikTok Leads ← Messenger/Instagram ← المكالمات الفائتة. معالج ربط القنوات للمجمع. حساب تكلفة الرسائل وحد الإنفاق.
**معايير القبول:** كما في INTEGRATIONS_PLAN §12 + رسالة حقيقية من رقم اختبار تصل وتُرد في staging.

## المرحلة 6 — إدارة المواعيد (الكاملة)
**المهام:** التقويم حسب الفرع، إعادة الجدولة، كشف التعارض، تذكيرات الموظف، رسائل تأكيد وتذكير للعميل (قوالب)، الحضور/عدم الحضور، أسباب الإلغاء، واجهة `SchedulingAdapter`.
**معايير القبول:**
- [ ] كل انتقال حالة مسجل في `appointment_events`.
- [ ] التذكير يُرسل بتوقيت الفرع الصحيح (اختبار عبر مناطق زمنية).
- [ ] الحجز من المحادثة يُسند تلقائيًا للقناة والحملة.

## المرحلة 7 — التحليلات وأتمتة التسويق
**المهام:** جداول مجمّعة يومية، لوحة المجمع، تقارير القنوات/الحملات/الموظفين/القمع، التصدير، الموافقات وإلغاء الاشتراك، الحملات المسموحة، قواعد الأتمتة (تأكيد/تذكير/متابعة)، منع استخدام الفئات الحساسة.
**معايير القبول:**
- [ ] أرقام التقارير تطابق عيّنات يدوية من السجلات (100% على 3 مجمعات وهمية).
- [ ] رسالة ترويجية لعميل دون موافقة تُرفض في الخادم.
- [ ] فئة خدمة موسومة `is_sensitive` لا تظهر في أدوات بناء الجمهور.

## المرحلة 8 — الاشتراكات والمدفوعات
**المهام:** الباقات والأسعار حسب الدولة، التجربة، الترقية/التخفيض (Proration)، التجديد، الإلغاء، الحدود والاستحقاقات، الفواتير (PDF + حقول ضريبية)، `PaymentAdapter` + بوابة واحدة في sandbox، Dunning، صفحة التسعير العامة، تحليلات MRR.
**معايير القبول:**
- [ ] تكرار webhook الدفع لا يُنشئ فاتورة أو تجديدًا مزدوجًا.
- [ ] تجاوز حد المستخدمين يمنع الدعوة الجديدة برسالة واضحة.
- [ ] `past_due` → قراءة فقط بعد المهلة، والبيانات لا تُحذف.
- [ ] الفاتورة تحتوي الحقول التي اعتمدها المحاسب للسعودية.

## المرحلة 9 — الاختبار الأمني والإطلاق التجريبي
**المهام:** اختبار اختراق خارجي، مراجعة ASVS L2، إصلاح الثغرات، اختبار استعادة النسخ، خطة الحوادث، مراجعة قانونية سعودية + DPA + سياسة الخصوصية + الشروط، Runbooks، أدلة الاستخدام، تدريب تبسم بلس، تشغيل تجريبي ببيانات وهمية ثم حقيقية **بعد الموافقات فقط**.
**معايير القبول:**
- [ ] صفر ثغرات حرجة/عالية مفتوحة.
- [ ] استعادة ناجحة موثقة ضمن RTO/RPO المستهدف.
- [ ] توقيع المسؤول التقني والمستشار القانوني ومالك المنتج.
- [ ] قياس خط أساس (زمن الرد، الرسائل الضائعة، نسبة الحجز) قبل وبعد 4 أسابيع.

## المرحلة 10 — التوسع الدولي
لكل دولة: قائمة COUNTRY_LAUNCH_CHECKLIST كاملة ← Data Plane ← المحوّلات المحلية ← 2–3 مجمعات تجريبية ← فتح التسجيل.
الترتيب المقترح: مصر ← الإمارات ← بحسب الطلب (قطر/البحرين/عُمان/الكويت).

## قواعد العمل مع Claude Code في كل مرحلة
1. المعمارية والمهام ومعايير القبول أولًا ← التنفيذ ← الاختبارات وتشغيلها ← بوابات الجودة ← اعتماد بشري.
2. Pull Request لكل ميزة؛ مراجعة بشرية إلزامية للمصادقة والصلاحيات والـ RLS والمدفوعات.
3. لا بيانات حقيقية ولا مفاتيح إنتاج في الجلسات أو المستودع.
4. لا نشر للإنتاج ولا تفعيل رسائل حقيقية دون موافقتك الصريحة.
5. ملف `CLAUDE.md` في المستودع يلخّص هذه القواعد والأوامر.
